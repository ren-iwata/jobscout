# 11_architecture_audit — 完成形に対する現アーキテクチャ再監査

実施: 2026-07-19（CEO指示「本当に望むものが今のアーキテクチャで完成するのか再検討せよ」への回答）

## 結論

**土台は正しい。ただし完成形に必須の臓器が1つ欠けている——「非同期実行層」。** これを今すぐ足す（追加であり作り直しではない）。他の懸念2点（マルチテナント・レジストリ共有）は移行路が確保済みで、壁にならない。

## 監査の詳細

### 欠陥（要即対応）: 非同期実行層の不在
現構成は全てが「リクエスト駆動・60秒以内」のサーバーレス。しかし完成形の中核機能は長時間・定期実行を要する:
- 能力分析エンジン（リポジトリ解析＝分オーダー、定期再分析）
- v0.3メール自動取り込み（15分間隔ポーリング。Upworkは応募速度が競争力なので鮮度が価値）
- 通知・学習集計・定期ジョブ全般

対応（採択）: **PGのタスクキュー（js_tasks）＋GitHub Actionsワーカー**。理由: 新規アカウント・新インフラゼロ（既存のCI基盤・Secrets・DBをそのまま使う）、実行時間制限なし、ci-status方式でCTOが検収可能。頻度が上がりActions無料枠を圧迫したら Supabase pg_cron + Edge Functions へ移行（移行はワーカー実行環境の差し替えのみ。キュー設計は不変）。

### 懸念A: マルチテナント（壁ではない・計画移行）
現状はowner単独前提（cookie認証・データにuser_idなし）。ただし保存層は薄いドライバに隔離済みのため、`owner_id`列の追加＋認証の差し替え（Supabase Auth・loopで実績あり）は局所改修で済む。SaaS判断の時点で1〜2セッションの移行作業。JSONB中心の設計は学習集計に不利だが、当面の規模ではPGのJSONB検索で十分。必要になった列だけ抽出する。

### 懸念B: 2アプリの基盤重複とレジストリ共有（壁ではない・契約で解決）
agentfrontとjobscoutは同型基盤のコピーで、放置すると乖離コストが出る。ただし能力レジストリの共有は**同一DBを既に共有している**ため、テーブル契約（cap_*/js_kv）をインターフェースとして両アプリが読む形で成立する。コード共通化（モノレポ化）はSaaS本格化まで不要——今は「型を揃えておく」で足りる（evidence構造は既に同型）。

### 問題なしと確認した点
- 分析エンジン（ツール強制の構造化出力）: テナント数に対して線形スケール。設計変更不要
- 2段階分析（選別→精査）: SaaSのコスト構造そのもの。正しい
- 監査ログ・イベント駆動の記録: 学習層の生データとして設計済み
- CI一本化デプロイ・ci-status検収: 商用運用にそのまま耐える
- 「自動応募しない」境界: 商用時の最重要リスク（全ユーザーのアカウント保護）を最初から満たす

### 環境制約の記録（ワーカー設計に影響）
- Vercel: 関数60秒・Hobbyのcronは実質日次→定期実行の主体にできない（だからActions）
- GitHub Actions無料枠: private 2,000分/月→15分間隔常時ポーリングは超過（約5,700分/月）。時間毎なら収まる。高頻度が必要になった時点でpg_cron移行
- 能力分析v1の入力範囲: 公開リポ＋稼働URL＋自リポ（Actionsのgithub.token）。私有リポ横断はPATの対象追加（CEO1分）またはSaaS版のOAuthで解決

## 着手順（この監査に基づく確定）

1. 非同期実行層（js_tasksキュー＋Actionsワーカー＋検収路）……欠落臓器。全ての上物の前提
2. 能力分析エンジンv1（ワーカー上で稼働URL検証＋リポ解析→検証済みevidence自動生成→プロフィール同期）……SaaSの本丸を最小で実証し、構想の技術リスクを先に潰す
3. 検索クエリ自動生成（レジストリから導出・小）
4. v0.3メール取り込み（CEOのGmail一回設定が必要になった時点で）
5. 交渉レンジ承認・結果学習・マルチテナントは応募データとSaaS判断を待って着手
